# 値上げ交渉管理システム（営業価格申請アプリ）

各営業所の担当者が **顧客との交渉状況** と **合意価格の申請** を一元管理できるWebアプリです。
器具ごとに分かれていた現行のExcel管理表（東京中央支店）をそのまま取り込み、全器具を1つの画面で管理します。

## 主な機能

| 機能 | 内容 |
|---|---|
| ダッシュボード | 第1弾❺・第2弾❾の値上がり金額と目標達成率、器具区分別・担当者別の進捗 |
| 案件一覧 | 全器具の明細を一元表示。得意先・器具区分・担当者・ステータス・単価種別で絞り込み |
| 案件詳細 | ❶〜❾の値上げ状況、交渉ステータス・商談メモ・マスター単価種別の更新 |
| 合意価格の申請 | 明細を選択して合意単価を入力。目標達成率と承認ルートを自動計算 |
| 承認ワークフロー | 営業担当者 → 支店長 → 営業企画部。達成率により承認権限を自動判定 |
| 承認ルール設定 | 達成率の範囲と最終決裁者（支店長 / 営業企画部）を画面から自由に設定 |
| Excel取込 | 現行管理表（.xlsx）をアップロードするだけで取込・統合 |
| ログイン | 個人ごとのログインID/パスワード。役割に応じて操作範囲を制限 |
| ユーザー管理 | 営業企画部が担当者のIDを発行・パスワード初期化・利用停止 |
| 交渉履歴 | 商談の経緯を日付・手段・提示単価・結果つきで時系列に記録 |
| 添付ファイル | 見積書・稟議書類を案件や申請に添付（1ファイル3MBまで） |
| 通知 | 申請の提出・承認・差戻しを関係者に通知。外部Webhookにも送信可 |
| Excel書き出し | 現行管理表と同じ列構成で出力。絞り込み条件がそのまま反映される |
| 一括申請 | 得意先を選ぶと対象明細をまとめて1つの申請にできる |
| 目標設定 | 全社・支店・営業所・担当者の単位で目標金額を設定 |
| 複数支店対応 | 支店・営業所で絞り込み。担当者は自支店が既定、営業企画部は全社横断 |

## セットアップ（ローカル）

Node.js 22以上が必要です（DBは組み込みの `node:sqlite` を使うため追加インストール不要）。

```bash
npm install          # サーバー依存関係
npm run build        # フロントエンドのビルド（client/dist を生成）
npm start            # http://localhost:3000 で起動
```

### 最初のログイン

初期状態ではどのユーザーもパスワードが設定されておらず、**誰もログインできません**。
既定パスワードを埋め込むと変更を忘れたときにそのまま入られてしまうため、意図的にこの仕様にしています。
まず営業企画部（`planning`）のユーザーにパスワードを設定してください。

```bash
npm run set-password -- --list                 # ユーザーとログインIDの一覧
npm run set-password -- planning1              # 仮パスワードを生成して表示
npm run set-password -- planning1 <パスワード>  # パスワードを直接指定
```

ログイン後、画面の「ユーザー管理」から各営業所の担当者を追加できます。
追加時に仮パスワードが1度だけ表示されるので、本人に伝えてください（初回ログイン時に変更を求められます）。

### 現行管理表の取込

画面の「Excel取込」からアップロードするか、CLIで一括取込できます。

```bash
npm run import -- FH風呂釜.xlsx 業務部品.xlsx ビルトイン.xlsx
npm run import -- 管理表.xlsx --replace   # 既存データを消して取込
npm run reset-db                           # DB初期化（マスタ再seed）
npm run backup                             # DBバックアップ
```

## デプロイ

**Vercel（アプリ）＋ Turso（DB）** で公開できます。手順は **[DEPLOY.md](DEPLOY.md)** を参照してください。
自社サーバー向けにDocker / systemdの構成も同梱しています。

環境変数 `TURSO_DATABASE_URL` を設定するとTursoへ、未設定ならローカルのSQLiteファイルへ接続します
（アプリのコードは共通で、接続先だけが切り替わります）。

| 変数 | 用途 |
|---|---|
| `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN` | Turso接続情報。未設定時はローカルSQLite |
| `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` | アクセス保護。公開環境では必須 |
| `PORT` / `DATA_DIR` | 待受ポート / ローカルDBの保存先 |
| `NOTIFY_WEBHOOK_URL` | 通知の外部送信先（Teams / Slack の Incoming Webhook など）。未設定ならアプリ内通知のみ |
| `APP_BASE_URL` | Webhook本文に載せるリンクの基準URL（例: https://sales.paloma-pf.com） |
| `DEV_LOGIN_AS` | 開発時のみ。ログインを省略するログインID（本番では無効） |

### 開発時

```bash
npm run dev                    # APIサーバー（ポート3000）
cd client && npm run dev       # Vite開発サーバー（/api は3000へプロキシ）
```

機能開発中にログインが煩わしい場合は、`DEV_LOGIN_AS` に
ログインIDを指定すると、そのユーザーとしてログイン済みの状態で起動します。

```bash
DEV_LOGIN_AS=admin npm run dev       # 管理者としてログイン済みで起動
DEV_LOGIN_AS=sales1 npm run dev      # 営業担当者の画面を確認したいとき
```

役割ごとの画面の違いを確認したいときにも使えます。
**この指定は本番では無効です** — Vercel上、または `NODE_ENV=production` では
明示的に拒否してログを出し、通常どおり認証を要求します。

## 現行Excelとの対応（データの意味）

ヘッダー行（4行目）を自動検出し、**列名**で対応付けるため列位置のズレに強い取込になっています。

### 第1弾値上げ活動

| Excel列 | 意味 | アプリ内 |
|---|---|---|
| AB列 出荷単価 | ❶ 値上げ前単価 | `base_price` |
| AD列 新出荷単価 | ❷ 第1弾の目標値上げ単価（＝マスター単価となる） | `r1_target_price` |
| BL列 値上後単価 | ❸ 第1弾で妥結した値上後単価 | `r1_agreed_price` |
| BO列 | ❹ 値上がり単価 ＝ ❸−❶ | `r1_raise_unit`（自動計算） |
| BP列 | ❺ 値上がり金額 ＝ ❹×台数 | `r1_raise_amount`（自動計算） |

### 第2弾値上げ活動

| Excel列 | 意味 | アプリ内 |
|---|---|---|
| BS列 第２弾新値上げ単価 | ❻ 第2弾の目標値上げ単価 | `r2_target_price` |
| CG列 最終確定単価 | ❼ 第2弾値上げ後単価（CB列が「〇」で確定） | `r2_agreed_price` |
| CH列 | ❽ 第1弾からの更なる値上がり単価 ＝ ❼−❸ | `r2_raise_unit`（自動計算） |
| CI列 | ❾ 値上がり金額 ＝ ❽×台数 | `r2_raise_amount`（自動計算） |

**❺＋❾＝値上げ金額総数** としてダッシュボードに表示されます。
CB列（商談結果 記号入力）が「〇」の明細のみ第2弾の値上がりが有効になる仕様を再現しています。

## マスター単価（標準単価）6種類

目標値上げ単価は承認後にマスター単価となります。どの種類として登録されるかを案件・申請ごとに管理できます。

| No | 種別 | 区分 | 備考 |
|---|---|---|---|
| 1 | 取引先G商品G | 標準 | 掛率で登録 |
| 2 | 取引先G商品 | 標準 | 商品毎の価格対応 |
| 3 | 取引先商品G | 標準 | エリア毎の価格対応 |
| 4 | 取引先商品 | 標準 | |
| 5 | 納入先別単価 | 販売店対応 | 販売先と納入先が設定される |
| 6 | 見積伝票 | 物件対応 | 販売先と納入先が設定される |

取込時の初期値は次のルールで推定し、画面からいつでも変更できます。

1. 見積伝票番号あり → **6. 見積伝票（物件対応）**
2. 納入先コードが特定されている → **5. 納入先別単価（販売店対応）**
3. それ以外 → **4. 取引先商品**（②③は掛率・グループ設定に応じて担当者が指定）

## 承認ワークフロー

```
営業担当者（申請） → 支店長（承認） → 営業企画部（承認） → 承認済み・マスター単価登録
                        └─ 達成率がルールを満たす場合は支店長決裁で完結
```

- 申請時に **目標達成率 ＝ 申請値上金額 ÷ 目標値上金額** を自動計算
- 提出時に「設定 > 承認権限ルール」を上から順に評価し、最初に該当したルールの最終決裁者を適用
  - 既定: 達成率100%以上 → 支店長決裁で完結 ／ 100%未満 → 営業企画部決裁まで
  - ルール（達成率の範囲・決裁者）は営業企画部が画面から自由に追加・変更可能
- 差戻し時は申請者が修正して再提出可能
- **最終承認されると合意単価が案件明細（❸または❼）へ反映**され、選択した単価種別でマスター単価に登録される想定

## 技術構成

```
server/
  db.js          データアクセス層（ローカルSQLite / Turso を同一APIで抽象化）
  schema.sql     スキーマ・計算ビュー（deal_calc: ❹❺❽❾を自動計算）
  importer.js    現行管理表パーサー（ヘッダー名で列を自動対応付け）
  api.js         REST API（案件・申請・承認・ルール・設定・取込）
  auth.js        Basic認証・セキュリティヘッダー
  app.js         Expressアプリの組み立て（ローカル/Vercel共通）
  index.js       ローカル・コンテナ用の起動エントリ
api/index.js     Vercel Functions のエントリ
middleware.js    Vercel Edge Middleware（静的ファイルを含む全体の認証）
client/          React + TypeScript + Vite（SPA）
scripts/         CLI取込・DB初期化・バックアップ
deploy/          systemdユニット（自社サーバー運用向け）
```

## 認証とアクセス制御

個人ごとのログインID/パスワードで認証します。

| 項目 | 実装 |
|---|---|
| パスワード保存 | scrypt でハッシュ化（平文は保存しない） |
| セッション | HttpOnly + SameSite=Lax のCookie。有効期限8時間 |
| セッション保存先 | DB（サーバーレスでも共有できるようにするため） |
| 総当たり対策 | 5回連続failでアカウントを15分ロック |
| 仮パスワード | 初回ログイン時に変更を強制。変更するまで業務画面に入れない |
| パスワード変更時 | 他端末の既存セッションを全て切断 |
| APIの既定 | ログイン必須。公開するパスは明示的に列挙した3つのみ |

役割ごとの権限は次のとおりです。

| 操作 | 営業担当者 | 支店長 | 営業企画部 |
|---|---|---|---|
| 案件の参照・交渉状況の更新 | ○ | ○ | ○ |
| 申請の作成・提出 | ○ | ○ | — |
| 支店長としての承認 | — | ○（自支店のみ） | — |
| 営業企画部としての承認 | — | — | ○ |
| 承認ルール・目標金額の設定 | — | — | ○ |
| ユーザー管理 | — | — | ○ |

`BASIC_AUTH_USER` / `BASIC_AUTH_PASS` を設定すると、サイト全体にBasic認証がかかります。
アプリのログインとは別物で、インターネットに公開する場合の追加の壁として任意で使えます
（社内ネットワーク限定で運用する場合は不要です）。

## 現時点での制約

- ユーザー・支店マスタはseedデータ（`server/db.js`）。実際の組織に合わせて登録してください
- 目標金額の初期値は管理表から読み取った値（設定画面から変更可能）
- 承認済み申請の単価は本システム内の案件に反映されます。基幹システムのマスター単価への連携は今後の拡張ポイントです
- Vercel経由の画面アップロードは約4MBが上限です。大きい管理表はCLI（`npm run import`）から投入してください
