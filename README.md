# 値上げ単価管理システム

各営業所の担当者が **値上げ単価** と **顧客との交渉状況** を一元管理できるWebアプリです。
器具ごとに分かれていた現行のExcel管理表（東京中央支店）をそのまま取り込み、全器具を1つの画面で管理します。

**単価だけの管理表**のため、台数や金額の集計は扱いません。

## 主な機能

| 機能 | 内容 |
|---|---|
| 案件一覧 | 器種ごとの値上げ単価を一元管理。基本情報と値上げ状況を1画面で確認 |
| 弾ごとの入力 | 第1弾・第2弾それぞれに合意単価と適用年月を入れ、弾ごとに完了にできる |
| 目標単価の修正 | 目標値上げ単価❷❻は管理者のみ変更可能 |
| 交渉情報・履歴 | 法人（本部）ごとに交渉状況・メモ・商談履歴を記録 |
| Excel取込 | 管理表（.xlsx）を取込・統合。列の並びや見出しが違っても項目名で対応づけ。ファイルサイズの上限なし |
| Excel書き出し | 絞り込み条件がそのまま反映される |
| ログイン | 個人ごとのログインID/パスワード |
| 管理者画面 | 管理者が担当者のIDを発行・名簿の一括登録・利用停止 |
| 添付ファイル | 見積書などを案件に添付（1ファイル3MBまで） |

## セットアップ（ローカル）

Node.js 22以上が必要です（DBは組み込みの `node:sqlite` を使うため追加インストール不要）。

```bash
npm install          # サーバー依存関係
npm run build        # フロントエンドのビルド（client/dist を生成）
npm start            # http://localhost:3000 で起動
```

### 最初のログイン

初期状態ではどのユーザーもパスワードを持ちません。
既定パスワードを埋め込むと変更を忘れたときにそのまま入られてしまうため、意図的にこの仕様にしています。

**画面から設定する場合（ターミナル不要）**

デプロイ後にトップページを開くと「初期セットアップ」画面が表示されます。
管理者または営業企画部のユーザーを選んでパスワードを設定すると、そのままログインした状態になります。
この画面は **パスワードを持つ利用者が1人も居ない間だけ** 表示され、
1人でも設定されると二度と表示されません（APIも410を返して閉じます）。

**コマンドから設定する場合**

```bash
npm run set-password -- --list                 # ユーザーとログインIDの一覧
npm run set-password -- planning1              # 仮パスワードを生成して表示
npm run set-password -- planning1 <パスワード>  # パスワードを直接指定
```

いずれの方法でも、以降の担当者は画面の「管理者画面」から追加できます。
追加時に仮パスワードが1度だけ表示されるので、本人に伝えてください（初回ログイン時に変更を求められます）。

### 管理者画面（ユーザー）

**管理者（admin）のみ**が開けます。

**名簿の一括登録**

「記入例をダウンロード」で雛形を取得し、埋めて取り込みます。列は次のとおりです。

| 列 | 必須 | 内容 |
| --- | --- | --- |
| ログインID | ○ | 半角英数字と `._-` の3〜32文字 |
| 氏名 | ○ | |
| 役割 | | 営業担当者 / 支店長 / 営業企画部 / 管理者（省略時は営業担当者） |
| 支店 | | |
| 営業所 | | |
| 有効 | | 「×」で停止状態として登録 |

- 既に登録済みのログインIDは既定で見送ります。「既に登録済みのログインIDは内容を更新する」を選ぶと更新します。
- 1行でも不備があればその行だけ飛ばし、行番号と理由を返します（他の行は取り込まれます）。
- 発行された仮パスワードは取込結果の一覧にのみ表示されます。画面を離れると再表示できません。

### 現行管理表の取込

画面の「Excel取込」から取り込むか、CLIで一括取込できます。

**画面から取り込む場合**

ファイルはブラウザ側で読み取り、行データだけを500行ずつ送ります。
そのため **ファイルの大きさによる上限はありません**（Vercelのリクエスト上限に影響されません）。

見出し行を自動で探し、**列の項目名**で対応づけます。
支店や器具によって列の並び・見出しが違っても、そのまま取り込めます。

- 「器種名／機種名／商品名」「売上担当者支店名／支店名」のような表記の違いは自動で吸収します
- 自動で当たらなかった列は「列の対応」の表で選び直せます
- 必須項目（出荷単価・目標値上げ単価）が未対応のままだと取込ボタンは押せません
- 取り込まない列も同じ画面で確認できます

**CLIから取り込む場合**

```bash
npm run import -- FH風呂釜.xlsx 業務部品.xlsx ビルトイン.xlsx
npm run import -- 管理表.xlsx --replace   # 既存データを消して取込
npm run import -- 管理表.xlsx --force     # 取込済みでも入れ直す
npm run reset-db                           # DB初期化（マスタ再seed）
npm run backup                             # DBバックアップ
```

一度取り込んだファイルと同じ内容のものは、既定でスキップします（明細が二重になるためです）。
Excelを開いて保存し直しただけのファイルも、データの指紋で同じ内容と判定して止めます。
誤って取り込んだ場合は「Excel取込」画面の取込履歴から**取り消し**できます。

## デプロイ

**Vercel（アプリ）＋ PostgreSQL（DB）** で公開できます。

- **[SETUP-WEB.md](SETUP-WEB.md)** — ブラウザの管理画面だけで公開する手順（ターミナル不要）
- **[DEPLOY.md](DEPLOY.md)** — CLIを使う場合の詳細手順・独自ドメイン・バックアップ

自社サーバー向けにDocker / systemdの構成も同梱しています。

環境変数 `DATABASE_URL` を設定するとPostgreSQLへ、未設定ならローカルのSQLiteファイルへ接続します
（アプリのコードは共通で、接続先だけが切り替わります）。

| 変数 | 用途 |
|---|---|
| `DATABASE_URL` | PostgreSQLの接続文字列。未設定時はローカルSQLite |
| `DB_SCHEMA` | テーブルを作成するスキーマ名（既定: `sales_pricing`）。既存DBと衝突させないため |
| `DB_SSL_NO_VERIFY` | `true` で接続時のTLS証明書検証を緩める（社内認証局を使っている場合） |
| `BASIC_AUTH_USER` / `BASIC_AUTH_PASS` | アクセス保護。公開環境では必須 |
| `PORT` / `DATA_DIR` | 待受ポート / ローカルDBの保存先 |
| `BCRYPT_ROUNDS` | パスワードハッシュのコスト（既定10。ポータル側と揃えてください） |
| `DEV_LOGIN_AS` | 開発時のみ。ログインを省略するログインID（本番では無効） |
| `DISABLE_AUTH` | `true` にするとログインを不要にする。**本番でも有効になる**ため、社外から到達できる環境では使用しないでください |

### 開発時

```bash
npm run dev                    # APIサーバー（ポート3000）
cd client && npm run dev       # Vite開発サーバー（/api は3000へプロキシ）
```

機能開発中にログインが煩わしい場合は、`DEV_LOGIN_AS` に
ログインIDを指定すると、そのユーザーとしてログイン済みの状態で起動します。

```bash
DEV_LOGIN_AS=admin npm run dev       # 管理者としてログイン済みで起動
DEV_LOGIN_AS=sales1 npm run dev      # 営業担当者の画面を確認したいとき
```

役割ごとの画面の違いを確認したいときにも使えます。
**この指定は本番では無効です** — Vercel上、または `NODE_ENV=production` では
明示的に拒否してログを出し、通常どおり認証を要求します。

## 現行Excelとの対応（データの意味）

ヘッダー行（4行目）を自動検出し、**列名**で対応付けるため列位置のズレに強い取込になっています。

### 第1弾値上げ活動

| Excel列 | 意味 | アプリ内 |
|---|---|---|
| AB列 出荷単価 | ❶ 値上げ前単価 | `base_price` |
| AD列 新出荷単価 | ❷ 第1弾の目標値上げ単価（＝マスター単価となる） | `r1_target_price` |
| BL列 値上後単価 | ❸ 第1弾で妥結した値上後単価 | `r1_agreed_price` |
| BO列 | ❹ 値上がり単価 ＝ ❸−❶ | `r1_raise_unit`（自動計算） |

### 第2弾値上げ活動

| Excel列 | 意味 | アプリ内 |
|---|---|---|
| BS列 第２弾新値上げ単価 | ❻ 第2弾の目標値上げ単価 | `r2_target_price` |
| CG列 最終確定単価 | ❼ 第2弾値上げ後単価（CB列が「〇」で確定） | `r2_agreed_price` |
| CH列 | ❽ 第1弾からの更なる値上がり単価 ＝ ❼−❸ | `r2_raise_unit`（自動計算） |

台数を掛けた金額（BP列❺・CI列❾）は扱いません。単価だけの管理表のためです。
取込時は、第1弾は❸が❶を上回っていれば完了、第2弾はCB列が「〇」なら完了として引き継ぎます。

## マスター単価（標準単価）6種類

目標値上げ単価はマスター単価となります。どの種類として登録されるかを案件ごとに管理できます。

| No | 種別 | 区分 | 備考 |
|---|---|---|---|
| 1 | 取引先G商品G | 標準 | 掛率で登録 |
| 2 | 取引先G商品 | 標準 | 商品毎の価格対応 |
| 3 | 取引先商品G | 標準 | エリア毎の価格対応 |
| 4 | 取引先商品 | 標準 | |
| 5 | 納入先別単価 | 販売店対応 | 販売先と納入先が設定される |
| 6 | 見積伝票 | 物件対応 | 販売先と納入先が設定される |

取込時の初期値は次のルールで推定し、画面からいつでも変更できます。

1. 見積伝票番号あり → **6. 見積伝票（物件対応）**
2. 納入先コードが特定されている → **5. 納入先別単価（販売店対応）**
3. それ以外 → **4. 取引先商品**（②③は掛率・グループ設定に応じて担当者が指定）

## 弾ごとの進め方

第1弾・第2弾は**独立して**進みます。片方が完了しても、もう片方はそのまま続けられます。

| 状態 | 意味 |
|---|---|
| 未入力 | 合意単価がまだ入っていない（または現行単価から上がっていない） |
| 合意済 | 合意単価は入ったが、まだ完了にしていない |
| 完了 | 営業担当者が「完了」にした |

案件一覧の「入力」から、弾ごとに **合意単価** と **適用年月** を入れて「完了」にします。
完了にするには合意単価が必要です（空や0のままでは完了にできません）。
適用年月は `2026-04` の形式です（`2026/4` や `202604` も受け付けて変換します）。

**目標値上げ単価❷❻は管理者のみ変更できます。** 目標が誰でも動かせると進捗の意味が無くなるためです。

## 交渉情報・交渉履歴（法人ごと）

単価は器種ごとでも、交渉そのものは法人（本部）単位で進みます。
そのため交渉状況・メモ・商談履歴は**法人に紐づけて**記録します。

- 案件一覧の法人名をクリックすると、その法人の交渉情報が開きます
- 交渉状況（未着手 / 交渉中 / 合意 / 値上げ不可）・直近の商談日・メモを保存できます
- 商談履歴は日付・手段・結果・内容つきで時系列に残ります
- 同じ法人のどの明細から見ても、同じ交渉情報・履歴が表示されます

## 技術構成

```
server/
  db.js          データアクセス層（ローカルSQLite / PostgreSQL を同一APIで抽象化）
  schema.sql     スキーマ（SQLite用）・計算ビュー（deal_calc: ❹❽と弾ごとの状態）
  schema.postgres.sql  スキーマ（PostgreSQL用。専用スキーマに配置）
  fields.js      取り込める項目の定義（見出しの別名・必須の判定）
  importer.js    現行管理表パーサー（項目名で列を対応付け）
  api.js         REST API（案件・法人ごとの交渉情報・取込）
  auth.js        Basic認証・セキュリティヘッダー
  app.js         Expressアプリの組み立て（ローカル/Vercel共通）
  index.js       ローカル・コンテナ用の起動エントリ
api/index.js     Vercel Functions のエントリ
middleware.js    Vercel Edge Middleware（静的ファイルを含む全体の認証）
client/          React + TypeScript + Vite（SPA）
scripts/         CLI取込・DB初期化・バックアップ
deploy/          systemdユニット（自社サーバー運用向け）
```

## 認証とアクセス制御

個人ごとのログインID/パスワードで認証します。

| 項目 | 実装 |
|---|---|
| パスワード保存 | bcrypt でハッシュ化（社内ポータルと同方式。平文は保存しない） |
| セッション | HttpOnly + SameSite=Lax のCookie。有効期限8時間 |
| セッション保存先 | DB（サーバーレスでも共有できるようにするため） |
| 総当たり対策 | 5回連続failでアカウントを15分ロック |
| 仮パスワード | 初回ログイン時に変更を強制。変更するまで業務画面に入れない |
| パスワード変更時 | 他端末の既存セッションを全て切断 |
| APIの既定 | ログイン必須。公開するパスは明示的に列挙したものだけ |
| 既存ハッシュ | ポータル（bcryptjs）が作成したハッシュをそのまま照合できる |

役割ごとの権限は次のとおりです。

| 操作 | 営業担当者 | 支店長 | 営業企画部 | 管理者 |
|---|---|---|---|---|
| 案件の参照 | ○ | ○ | ○ | ○ |
| 合意単価・適用年月の入力／完了 | ○ | ○ | ○ | ○ |
| 目標値上げ単価❷❻の変更 | — | — | — | ○ |
| 交渉情報・履歴の記録 | ○ | ○ | ○ | ○ |
| Excel取込 | ○ | ○ | ○ | ○ |
| ユーザー管理 | — | — | — | ○ |

`BASIC_AUTH_USER` / `BASIC_AUTH_PASS` を設定すると、サイト全体にBasic認証がかかります。
アプリのログインとは別物で、インターネットに公開する場合の追加の壁として任意で使えます
（社内ネットワーク限定で運用する場合は不要です）。

## 社内ポータルとの関係

パスワードのハッシュ方式は社内ポータル（NextAuth.js v4）と同じ **bcryptjs** に揃えてあります。
そのため、ポータルが作成した既存のハッシュをそのまま照合でき、同じユーザーテーブルを
共有する構成も取れます（コストは `BCRYPT_ROUNDS` でポータル側に合わせられます）。

本アプリのテーブルは専用スキーマ `sales_pricing` に置くため、ポータルのテーブルとは衝突しません。

**ポータルからのSSO（HMAC署名トークン）には未対応です。** 現状このアプリは独自のログイン画面を
持っており、アカウントはポータルと別管理になります。対応する場合はトークンの仕様
（署名対象・アルゴリズム・受け渡し方法・有効期限・共有シークレット）が必要です。

## 現時点での制約

- ユーザー・支店マスタはseedデータ（`server/db.js`）。実際の組織に合わせて登録してください
- 合意単価は本システム内で管理します。基幹システムのマスター単価への連携は今後の拡張ポイントです
